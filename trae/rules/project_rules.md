# 项目开发规则（面向 AI）

> 适用项目：Firefox 英文网页翻译插件（`chrome-extension-en-translation`）
> 本规则供 AI 在项目开发中遵循，侧重高层面指导原则；具体技术细节以 [docs/design.md](../../docs/design.md) 为准。

## 1. 项目概览

- 本项目是 Firefox 浏览器扩展：提取英文网页文章 → 转换为 Markdown → 调用 AI（Qwen，OpenAI 兼容协议）翻译为中文 → 打字机效果展示 → 本地持久化最近一次结果。
- 全流程基于需求文档 [docs/proposal.md](../../docs/proposal.md)、架构文档 [docs/design.md](../../docs/design.md)、布局文档 [docs/layouts](../../docs/layouts/) 与任务拆分 [docs/task.md](../../docs/task.md)。

## 2. 语言与框架

- **语言**：统一使用 TypeScript，禁止滥用 `any`；跨模块数据必须使用共享类型定义。
- **UI 框架**：React。
- **构建工具**：Vite（多入口：Content Script / Background / Popup / Options）。
- **浏览器平台**：仅面向 Firefox，基于 WebExtensions 标准，不引入 Chrome 专用 API 假设。

## 3. NPM 包管理

- 包管理器统一使用 **npm**，使用 `package-lock.json` 锁定依赖版本。
- 新依赖的引入须与架构文档一致，优先使用以下既定依赖；确有新增需求时先说明用途：
  - `@mozilla/readability`（文章提取）、`turndown`（HTML→Markdown）
  - `openai`（OpenAI 兼容接口调用，配合 Qwen）
  - `md-wx`（Markdown 渲染组件）、`react` / `react-dom`
  - `typescript` / `vite` / ESLint / Prettier（工程化）
- 不引入冗余依赖；能复用既定方案时不新增库。

## 4. 项目目录结构

- 遵循架构文档 [docs/design.md](../../docs/design.md) §5 的目录结构，核心约定：
  - `src/content/`：注入页面的提取与转换逻辑，不承载 UI。
  - `src/background/`：后台消息路由、AI 翻译调用、持久化读写。
  - `src/popup/`、`src/options/`：React 界面（主界面 / 设置页）。
  - `src/shared/`：跨模块共享的类型、常量、消息协议，模块间不得绕过它直接互调。
  - `docs/`：需求、架构、布局、任务等文档；`trae/rules/`：本规则。
  - 构建产物输出到 `dist/`，`public/` 存放 manifest 等扩展静态资源。
- 目录小写、单词间用短横线连接（kebab-case）；文件同目录命名规范，组件文件使用 `.tsx`。

## 5. 代码风格

- 使用 ESLint + Prettier 统一风格（缩进 2 空格、单引号、末尾分号），提交前必须通过检查。
- 命名规范（详见 design.md §6.2）：
  - 变量 / 函数：camelCase；组件 / 类：PascalCase；常量：UPPER_SNAKE_CASE；类型 / 接口：PascalCase。
- 注释使用中文；公共函数与复杂逻辑必须写明作用与关键约束。
- 模块单一职责；模块间只通过 `src/shared/messages.ts` 定义的消息协议通信，禁止互相直接调用。

## 6. 错误处理与安全

- 异常（网络、鉴权、提取失败、限流、超时）必须显式处理，向上层返回结构化错误（错误码 + 用户可读信息），禁止吞掉异常。
- API Key 等敏感信息仅存于本地存储，仅在 Background 层读取，不得注入页面上下文或 Content Script。
- 不信任页面内容：提取与转换只做文本处理；渲染译文时不直接注入 HTML（经 md-wx 按 Markdown 解析渲染）。
- 遵循最小权限原则：manifest 仅申请功能必需的权限。

## 7. AI 助手任务执行规范

### 7.1 任务范围控制

- **严格按照任务拆分执行**：必须严格按照 [docs/task.md](../../docs/task.md) 中定义的任务模块（T1 ~ T7）范围执行，不得超出指定任务的边界。
- **单一任务原则**：每次只执行一个明确指定的任务（如「任务 T1」「任务 T2」），完成后等待用户确认再进行下一步。
- **禁止自动扩展**：不得基于架构文档或其他文档自行扩展任务范围；如需扩展，必须先通知用户并取得确认。

### 7.2 任务指令格式

用户应使用以下格式明确指定任务：

- **明确任务编号**：「请执行任务 T1：[工程脚手架搭建]」
- **范围限制**：「只完成 T1 中列出的具体内容，不要超出范围」
- **停止指令**：「完成后等待我确认再进行下一步」

### 7.3 执行验收标准

- **任务完成确认**：每个任务完成后，必须对照 [docs/task.md](../../docs/task.md) 中该任务的「验收 / 可见效果」进行自检。
- **范围边界检查**：确保所有创建和修改的文件都在指定任务范围内。
- **等待用户确认**：任务完成后总结完成情况与验证结果，等待用户确认后再进入下一个任务，不擅自继续。

### 7.4 异常处理

- **任务描述不清晰**：如果任务描述不清晰，应先询问具体范围，而不是自行决定。
- **依赖关系处理**：如果当前任务依赖其他未完成任务，应明确指出依赖关系（参考 task.md 的依赖列），并等待用户指示，不跳过依赖强行实现。
- **超出范围的代码**：如果发现已创建超出任务范围的代码或文件，应主动询问用户是否需要清理。

## 8. 文档驱动

- 所有开发行为以 `docs/` 下文档为唯一依据：需求、架构、布局、任务。
- 实现中如发现文档与实现冲突，先记录并询问用户，不擅自修改文档或实现。
